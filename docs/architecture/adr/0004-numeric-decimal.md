# ADR-0004：NUMERIC + Decimal 端到端，而非浮点或整数最小单位

- 状态：已接受
- 日期：2026-11-06
- 相关：`docs/architecture/data-model.md` §1.2

## 上下文

系统所有"钱"和"价"都来自 OKX 的**十进制字符串**：`tickSz="0.01"`、`lotSz="0.01"`、`ctVal="1"`、`last="343.28"`，且不同标的的最小变动单位不同（0.01、0.001、0.0001）。回测要求同参数两次结果**逐位一致**，验收要求误差 <1e-6，任何浮点累加都会破坏可复现性。

## 决策

- PostgreSQL：价格 `NUMERIC(20,10)`，数量/金额 `NUMERIC(24,10)`，比率 `NUMERIC(12,10)`。
- Python：金额与价格一律 `decimal.Decimal`，从解析到落库到序列化不经过 `float`。
- API：`Decimal` 以**字符串**返回（`"343.68"`），前端不做浮点运算。
- 统计计算（相关系数、聚类距离、指标）内部允许 `float64`（numpy/scipy），但输出必须显式 `quantize(Decimal("1e-10"))` 后入库，并在单测中以 1e-9 容差比对。

## 后果

正面：

- 与交易所的十进制字符串表示同构，无"0.1+0.2"类语义错误。
- 回测成本累加（手续费、滑点、资金费）可逐位复现。
- 数值范围足够：`NUMERIC(20,10)` 可表示 1e10 量级价格与 1e-10 精度。

负面 / 代价：

- 比 `float8`/`bigint` 慢（可忽略：P1 写路径是批量 upsert，读路径是聚合）。
- 代码纪律要求高：任何引入 `float` 的金额计算都是缺陷，必须在评审中拦截（可用 `Decimal` 类型标注 + lint 规则辅助）。
- 与 pandas/numpy 交互时需要显式转换，容易在"统计 → 落库"边界漏掉量化。

## 为什么不是其它方案

| 备选 | 拒绝理由 |
| --- | --- |
| `float8` / Python `float` | 二进制无法精确表示十进制小数，累加顺序不同结果不同，回测不可复现；金额误差会随交易次数放大 |
| 整数最小单位（bigint ticks，如"分"或 1e-8 单位） | 每个标的的 scale 不同（tickSz 0.01 vs 0.001），需要维护 per-instrument scale 元数据与全链路换算；跨标的聚合与比率计算要反复缩放，出错面更大 |
| 字符串存全部数值 | 无法在 SQL 中聚合与排序（或需强转，失去意义），分区与索引效率差 |

## 复核触发条件

若未来出现每秒百万级 tick 写入（P3 实时行情），评估将写入路径改为整数最小单位或列式存储，但**对外契约仍保持 Decimal 字符串**。
