# trading — 个人量化交易工作台

## 项目定位

开发一个名为 **trading** 的本地个人量化交易研究与执行系统。

这是一个只服务于单个用户的个人工具，不是 SaaS，不需要多用户、多租户、权限体系、团队协作或复杂的云端基础设施。

核心理念是**通过理解标的之间的关系，而不是孤立地分析单只标的，发现更有价值的组合交易机会**。系统通过分析标的之间的动态相关性、市场共振、趋势和相对强弱，发现交易机会并构建多空组合策略，最终通过 OKX 执行 `SPOT` 与 `SWAP` 两类标的的交易。

这是一个以确定性量化模型和规则引擎为核心、人工审批和风险控制为约束的个人交易系统：不是高频交易系统，也不是由 AI 自主决定买卖的交易机器人。持仓周期是可配置的策略参数，剥头皮、日内、波段只是同一套策略框架下的不同参数组合，不单独设计独立的短周期系统。

系统的核心工作流程就是 §三.5 的策略生命周期八阶段——机会发现 → 策略生成 → 人工审核 → 历史回测 → 量化验证 → 模拟交易 → 实盘授权 → 实盘运行，之后是交易复盘。

## 一、核心设计原则

### 1. 以策略为核心

Watchlist 是日常使用入口，Strategy 和 Backtest 是产品核心。

用户主要工作是：
- 观察自己关注的资产。
- 查看 K 线和技术指标。
- 设计交易策略。
- 调整策略参数。
- 对单个或多个资产进行批量回测。
- 根据回测结果选择适合的策略。
- 将策略用于手动交易或自动交易。

不要将产品设计成以财经新闻、股票资讯或 AI 问答为中心的应用。

### 2. 数据驱动，AI 辅助

行情、技术指标、策略信号、回测和订单执行必须由确定性的程序完成。

AI 主要负责：
- 解释市场和技术指标。
- 分析策略表现。
- 辅助理解回测结果。
- 根据用户需求提出策略和参数候选方案。
- 总结交易复盘。

AI 不直接计算行情指标，不绕过策略引擎产生交易订单，也不拥有交易所 API 凭证。

### 3. 模块化但不过度设计

采用模块化单体架构。

每个业务模块有明确职责和接口。

新增技术指标、策略、数据源或交易功能时，尽量通过增加模块实现，不影响已有模块。

不引入微服务、分布式消息系统、复杂插件市场或多 Agent 协作架构。

### 4. 本地优先

- 本地独立运行。
- 使用本地持久化存储。
- 使用本地 PostgreSQL 持久化存储；表结构只经 Alembic 版本化迁移变更，不在代码里建表。
- 历史行情较大时允许使用 Parquet 等本地列式文件存储。
- API Key 通过本地配置注入。
- 不要求云端服务或 Kubernetes。

## 二、交易标的

第一版同时支持 OKX 的两类交易标的：`SPOT`（现货，例如 `BTC-USDT`、`XAAPL-USDT`）与 `SWAP`（USDT 本位永续，例如 `BTC-USDT-SWAP`、`AAPL-USDT-SWAP`）。同一产品的两种形态共用同一套指标、策略与回测代码，标识、行情与交易规则分别维护，映射由标的模块统一维护；两种形态能在页面上直接切换。

**类别是可扩展维度，不是布尔开关。** 每个类别的精度、最小下单量、杠杆、保证金与资金费分别维护（交易时段不在此列，另按标的所属资产判，见下）；新增类别（例如接入真实美股）只增加一个类别的实现，不修改已有类别的计算逻辑。类别差异只在标的模块的「按类别的交易规则集合」里定义一次，其他模块查表取值，不写散落的 `inst_type` 分支。

### 交易类别与资产

类别与资产是两个独立维度：类别决定交易规则（精度、最小下单量、杠杆、保证金、资金费），资产决定行情来源与交易时段。

**类别：SPOT / SWAP**

| 维度 | SPOT | SWAP |
| --- | --- | --- |
| 交易规则 | 精度与最小下单量按现货 | 精度、最小下单量与合约面值按永续 |
| 杠杆与保证金 | 没有杠杆，不涉及保证金 | 有杠杆与保证金；逐仓、净持仓 |
| 资金费 | 无此概念 | 按结算期计费，计入持仓成本 |
| 持仓来源 | 由账户余额明细推导 | 交易所独立的持仓接口 |

交易时段由标的所属资产决定，不由类别决定。`SPOT` 与 `SWAP` 都既可能是加密资产，也可能是代币化股票，两类标的的交易时段完全不同：`BTC-USDT-SWAP` 与 `BTC-USDT` 全天候交易，`AAPL-USDT-SWAP` 与 `XAAPL-USDT` 按美股盘前 / 正常 / 盘后 / 休市。因此类别规则集合不承载时段语义，`TradingRules.session_kind` 仅作为资产类型缺失时的兜底默认值，不得作为判定依据。

**资产：crypto / tokenized_equity / commodity_token**

- `crypto`：加密货币，例如 `BTC-USDT`、`ETH-USDT`、`SOL-USDT`，以及对应的 `BTC-USDT-SWAP` 等永续。
- `tokenized_equity`：OKX 上的代币化美股与 ETF，例如 `XAAPL`、`XNVDA`、`XTSLA`、`XSPY`、`XQQQ`，以及对应的 `AAPL-USDT-SWAP` 等永续。
- `commodity_token`：代币化商品，沿用上游已存在的资产类别。

两个维度可以组合：`BTC-USDT`（SPOT × crypto）、`BTC-USDT-SWAP`（SWAP × crypto）、`XAAPL-USDT`（SPOT × tokenized_equity）、`AAPL-USDT-SWAP`（SWAP × tokenized_equity）。

具体可交易资产以当前账户和 OKX API 返回结果为准。

### 交易标的抽象

建立统一的 Instrument 模型。

至少包含：
- symbol / instId
- asset_type
- exchange
- base_currency
- quote_currency
- tick_size
- lot_size
- min_order_size
- listing_time
- trading_status
- inst_type（`SPOT` / `SWAP`）
- product_key（同一产品跨形态的配对键）
- data_start（可用行情起点）
- 仅 SWAP 非空：ct_val / ct_mult / ct_type / max_lever / settle_ccy

不同资产可以共用行情、技术指标和策略计算，但交易规则由对应的交易适配层处理。

不能将代币化股票直接视为传统美股。

需要保留交易时间、行情来源、数据可用区间和价格参考机制等信息。

### 现货与永续：同一产品的两种形态

现货（SPOT）与永续（SWAP）都是第一版支持的交易形态。同一个产品的两种形态共用同一套行情、技术指标、策略与回测代码，页面上可一键切换，切换时 K 线周期与指标参数保持不变。两种形态的价格可能因流动性与结算方式而偏离，界面必须同时显示另一形态的最新价与价差，不得暗示两者等价。

永续的价值是做空与杠杆。永续专属的合约参数（`ctVal`、`ctMult`、`ctType`、`maxLever`、`settleCcy`）只在交易适配层与执行/回测的保证金模型中生效，指标、策略与统计模块对形态无感知。

杠杆约束：`max_leverage` 默认 3、硬上限 10，单标的可用杠杆取 `min(max_leverage, instrument.maxLever)`，并按交易所 `position-tiers` 档位 clamp；保证金模式固定逐仓（isolated），持仓模式固定净持仓（net）。这些约束连同强平缓冲与自动止损要求，见「已生效决策」与 `decisions.md`。

资金费是永续持仓的成本：资金费必须计入回测 PnL，且默认开启。

真正的期货合约与更高杠杆档位不在第一版范围，但架构不能阻碍以后增加。

## 三、功能模块

### 1. Exchange

负责交易所连接和数据访问。

第一版实现 OKX Adapter。

负责：
- 获取可交易标的列表。
- 获取最新行情。
- 获取历史 K 线。
- 订阅 WebSocket 行情。
- 获取账户余额。
- 获取当前持仓。
- 查询订单和成交记录。
- 下单、撤单及订单状态同步。

行情接口和交易接口必须分离。

业务模块不能直接调用 OKX API。

交易所适配器负责处理：
- API 签名。
- 限流。
- 断线重连。
- 错误码。
- 请求超时。
- 交易产品精度。
- 订单状态映射。

所有交易请求必须保留本地唯一标识，避免网络重试导致重复下单。

### 2. Market

负责行情管理和历史数据。

支持：
- 最新价格。
- K 线 OHLCV。
- 成交量。
- 行情时间戳。
- 历史行情下载和缓存。
- 数据完整性检查。

统一使用 UTC 时间戳保存数据。

K 线必须能够识别：
- 已完成 K 线。
- 未完成 K 线。
- 缺失数据。
- 重复数据。
- 数据来源。
- 数据更新时间。

对于不同资产，需要允许不同的交易时段和行情连续性。

#### 混合行情与交易时段

行情是混合体系：同一个标的在不同时段可能来自不同来源，因此每根 K 线都必须带来源标识与市场状态，且不同来源、不同时段的数据不得未经处理直接混用。

- 美股正常交易时段：`tokenized_equity` 优先使用真实美股行情分析标的之间的关系。数据源允许使用第三方代理行情，但必须记录来源。
- 盘前与盘后：结合美股行情与 OKX 行情，并在数据上标明所处时段。
- 美股休市期间：使用 OKX 行情（加密资产全天候交易，代币化美股永续在休市期间仍会有价格波动），同时识别流动性不足、价格偏离与参考价格缺失的风险。
- 交易时段由标的所属资产决定，不由类别决定（完整判定见 §二「交易类别与资产」）：`crypto` 全天候交易，`tokenized_equity` 按美股盘前 / 正常 / 盘后 / 休市；`TradingRules.session_kind` 只是资产类型缺失时的兜底默认值，不作判定依据。

历史数据不足时，必须明确显示可用起止时间，禁止补造历史数据。

### 3. Watchlist

系统的主要日常入口。

支持：
- 添加和删除标的。
- 按资产类别和自定义分组。
- 搜索标的。
- 查看最新价格及涨跌幅。
- 查看成交量。
- 查看常用技术指标。
- 查看相关标的。
- 查看当前运行策略。
- 查看最近交易信号。
- 设置价格提醒。

Watchlist 支持用户选择资产范围，并将标的集合直接传递给回测模块。

不需要复杂的股票研究管理功能。

### 4. Indicator Engine

建立独立的技术指标计算模块。

第一版实现：
- SMA / MA
- EMA
- RSI
- MACD
- ATR
- Bollinger Bands
- VWAP
- Volume MA

统一指标计算接口。

每个指标需要定义：
- 名称。
- 参数。
- 输入数据。
- 输出字段。
- 计算逻辑。
- 最小数据长度。

新增指标时只需要增加实现并注册，不需要修改策略引擎和界面核心逻辑。

指标计算必须有单元测试，确保历史回测和实时计算结果一致。

支持同一标的多个周期的指标计算。

### 5. Strategy Engine

这是系统最重要的核心模块之一。

建立统一的策略接口。

策略负责读取行情与技术指标，结合用户配置的参数，输出标准化交易信号。

策略不能直接：
- 访问交易所 API。
- 修改账户余额。
- 创建订单。
- 修改持仓。
- 读写其他策略的内部状态。

每个策略必须定义：
- 策略 ID。
- 策略名称。
- 策略版本。
- 参数 Schema。
- 所需指标。
- 所需 K 线周期。
- 信号生成逻辑。
- 信号说明。

统一输出交易信号，例如：

```
{
  "strategy_id": "rsi_mean_reversion",
  "symbol": "BTC-USDT",
  "signal": "BUY",
  "timeframe": "1H",
  "price": 95000,
  "reason": "RSI crossed above oversold threshold",
  "timestamp": "2026-11-10T10:00:00Z"
}
```

信号类型至少支持：
- BUY
- SELL
- HOLD

必要时增加目标仓位或目标仓位比例字段。

第一版实现一些简单策略作为示例：
- MA Cross。
- RSI Mean Reversion。
- MACD Trend。
- Bollinger Bands。

这些示例策略只用于验证架构，不需要一次性实现复杂策略。

策略必须能够独立测试。

#### 策略生命周期（八阶段）

所有策略走同一条生命周期，任何阶段都不能被跳过；AI 辅助功能不得绕过这套流程，也不能绕过风险检查与实盘授权。

1. 机会发现：目标驱动（围绕目标标的分析关联标的）或市场驱动（扫描全部可交易标的找共振、趋势与相对强弱）。
2. 策略生成：由确定性程序把基础策略组件组合成完整策略，产出可配置、可回测、可复现的策略定义。
3. 人工审核：所有新策略必须经人工审核才能进入量化验证。
4. 历史回测：复用同一套策略与信号代码，在历史行情上跑回测，不读 `as_of` 之后的数据。
5. 量化验证：按用户自定的门槛判定（收益率、最大回撤、Sharpe Ratio、胜率、交易次数等）。不达标不允许通过人工审批绕过。
6. 模拟交易：用真实行情、本地模拟订单验证信号与执行链路。
7. 实盘授权：验证通过后还需按策略单独授权，受已批准的资金预算与风险限制约束。
8. 实盘运行：在授权与风控约束内运行，随时可被紧急停止。

### 6. Backtest

这是 P0 核心功能。

建立独立的回测引擎，复用 Strategy Engine 的策略和信号生成逻辑。

不允许回测和实盘分别实现两套策略代码。

#### 回测配置

用户可以选择：

**策略**
- 选择策略。
- 配置参数。

**标的范围**
- 单个标的。
- Watchlist 全部标的。
- 指定分组。
- 用户手动选择的多个标的。
- 当前 OKX 支持的全部可交易标的。

**市场周期**
- 15m。
- 1H。
- 4H。
- 1D。
- 其他实际数据源支持的周期。

**历史区间**
- 开始日期。
- 结束日期。

**资金配置**
- 初始资金。
- 计价货币。
- 每笔交易金额。
- 最大持仓比例。

**交易成本**
- Maker / Taker 手续费。
- 滑点。
- 买卖价差的估算。
- 资金费（仅永续）：按 8 小时结算点、以 `notional × realizedRate` 计入持仓 PnL，正费率多头付出、空头收取；缺失时标记覆盖缺口，不得静默按 0 处理。
- 其他适用费用。

#### 回测结果

每次回测至少输出：

- 初始资金。
- 最终资金。
- 总收益率。
- 年化收益率（适用时）。
- 最大回撤。
- 胜率。
- 盈亏比。
- Profit Factor。
- Sharpe Ratio。
- 交易次数。
- 平均持仓时间。
- 单笔最大盈利。
- 单笔最大亏损。
- 资金费总额与资金费覆盖率（仅永续；覆盖率不足时报告必须显式标注）。
- 数据来源标识，取值限定为 `okx`、`okx_spot`、`okx_swap`、`us_equity_proxy` 之一。

同时保存：
- 每笔交易记录。
- 买卖时间。
- 买卖价格。
- 交易数量。
- 手续费。
- 交易原因。
- 收益变化。
- 资金曲线。

#### 批量回测

支持对多个标的执行相同策略。

例如用户选择 RSI 策略，对 Watchlist 中所有资产进行回测，输出资产表现排行榜。

支持：
- 按收益排序。
- 按最大回撤排序。
- 按 Sharpe Ratio 排序。
- 按 Profit Factor 排序。
- 过滤交易次数不足的结果。

区分单标的独立资金回测与多标的共享资金组合回测。

#### 参数组合测试

用户可以为策略参数指定一组候选值。

例如：

RSI Period：7、14、21
Oversold：20、25、30
Overbought：70、75、80

自动组合并执行回测。

保存每组参数的表现，方便横向对比。

不要自动将历史收益最高的参数视为最优参数。

提供训练区间、验证区间和样本外测试区间，帮助发现过拟合。

#### 回测正确性

重点保证：
- 不使用未来数据。
- 不允许未来函数。
- 只使用当时已经完成的 K 线数据。
- 订单成交价格必须符合配置的执行模型。
- 计入交易手续费和滑点。
- 处理同一根 K 线内止盈止损同时触发的歧义。
- 正确管理资金和同时持仓。
- 保留数据缺失和不可交易时段信息。

默认采用 K 线收盘后产生信号、下一根 K 线开盘或可配置执行价格成交的模型。

不同执行方式必须在结果中明确标注。

#### 代理数据源

允许使用真实美股日线行情作为代币化美股的代理回测数据源，用于补足代币化美股上市时间短（约 4 个月）的历史窗口。

代理数据必须遵守：只提供真实存在的周期（真实美股无 24 小时连续行情，不得合成 15m/1H 等周期）；每根 K 线标注来源与 `is_proxy`，与 OKX 行情分表存放；一次回测只使用单一数据源，禁止跨源拼接。代理结果不得与 OKX 实盘标的的回测结果混合排序或聚合，界面以徽标标注「代理数据，与实盘标的不可比」。

### 7. Execution

负责将策略信号转化为订单。

提供三种执行模式：

**Manual**
- 策略生成信号。
- 显示交易计划。
- 用户确认。
- 执行下单。

**Paper Trading**
- 使用真实行情。
- 本地模拟订单。
- 模拟成交、手续费及持仓变化。
- 不产生真实交易。

**Automated Trading**
- 策略信号自动进入执行流程。
- 经过风险检查后下单。
- 同步订单和成交状态。
- 处理订单失败、部分成交和撤单。

策略本身不关心执行模式。

不同执行模式共享策略信号接口。

自动交易默认关闭，需要用户明确启用。

从模拟切换到实盘必须二次确认：请求必须携带显式的风险确认标记，界面弹出二次确认，确认动作写入交易日志留痕。这是提醒而非资格门禁，不设置按天数或成交笔数的硬性门槛。

### 8. Risk Management

负责统一的交易风险约束。

第一版支持：
- 单笔最大交易金额。
- 单个标的最大持仓金额。
- 总持仓资金限制。
- 最大持仓数量。
- 杠杆上限（默认 3、硬上限 10，按档位 clamp）与强平缓冲检查（预估强平价距现价不足阈值时拒绝开仓）。
- 自动模式下开仓必须同时挂交易所侧止损，止损提交失败则整笔不开仓。
- 单日最大亏损。
- 止损和止盈。
- 重复信号防护。
- 订单数量与价格精度检查。
- 账户余额检查。

任何策略都不能绕过风险检查。

提供紧急停止开关。

自动交易发生异常时，默认停止新增订单，并保留当前持仓状态供用户处理。

不要擅自自动清仓。

### 9. Trading Journal

保存完整的策略和交易历史。

包括：
- 策略配置及版本。
- 回测结果。
- 模拟交易记录。
- 实盘交易记录。
- 策略信号。
- 订单及成交。
- 账户资金变化。

支持查看回测结果与实际交易表现的区别。

### 10. AI Assistant

作为后续扩展功能。

允许 AI 读取：
- Watchlist。
- 市场数据。
- 技术指标。
- 策略配置。
- 回测结果。
- 交易日志。

AI 可以：
- 解释当前市场状态。
- 分析技术指标。
- 解释策略表现。
- 提出参数调整候选方案。
- 比较不同策略。
- 总结交易复盘。

AI 可以建议创建策略配置和回测任务，但修改正式策略配置、启用自动交易和执行真实订单必须经过用户明确授权。

AI 不直接接触交易所 Secret Key。

新闻分析不是第一版开发重点，可以在后续增加。

### 11. Portfolio 组合管理

采用**全局统一决策 + 策略级虚拟持仓**。

- 每个目标标的可以拥有独立的策略实例和交易组合；市场驱动发现的机会也可以形成独立策略。
- 各策略独立核算自己的持仓、收益、成本和交易表现。
- 全局组合管理器统一负责：资金分配、总风险敞口与净敞口、重复持仓处理、多空冲突管理、组合集中度、策略优先级与总体风险管理。
- 真实 OKX 账户的订单与实际持仓由全局执行系统统一管理，并与策略级虚拟持仓核对。
- 用户可以设置策略资金预算、优先级和风险限制，系统在这些约束内自动分配资金。
- 运行中组合的成员、交易方向与目标权重调整必须经人工批准；独立风控触发的紧急减仓、止损和平仓不受该审批限制。

## 五、数据与架构约束

采用模块化单体。

建议模块边界：

- `core`（跨模块叶子层：错误、值对象、端口；不依赖任何业务模块）
- `api`（对外 HTTP 协议层，无领域逻辑）
- `db`（引擎、会话、声明基类、迁移入口）
- `exchange`
- `market`
- `instrument`
- `watchlist`
- `indicators`
- `strategy`
- `backtest`
- `execution`
- `risk`
- `journal`
- `shared`

表结构只经 Alembic 版本化迁移变更。当前表名为 `instruments`、`candles`、`funding`、`watchlists`、`watchlist_items`、`price_alerts`；迁移脚本在 `backend/migrations/`，配置在 `backend/alembic.ini`。

使用清晰的接口和数据模型。

模块不得随意访问其他模块的内部实现。

行情和历史 K 线需要缓存，避免每次回测重复下载。

回测结果必须保存策略版本、参数、数据范围、数据源和执行模型，以确保结果可以复现。

对于大量参数组合和多个标的的回测，使用本地任务队列和有限并发即可，不引入分布式计算系统。

## 六、安全要求

- 默认使用 OKX 模拟盘配置。
- API Key 和 Secret 仅保存在本地。
- 禁止提交凭证到 Git。
- API Key 最小权限原则。
- 禁止开通提币权限。
- 手动交易优先。
- 自动交易必须经过风险检查。
- 自动交易提供全局暂停开关。
- 下单必须进行幂等控制。
- 交易所状态和本地状态不一致时，以重新获取的交易所实际状态进行核对，不能盲目重复下单。

## 七、开发阶段

不要一次性实现全部功能。阶段按 P1–P4 划分，P0 是工程基座；节点顺序与阶段闸门判据见 [`v3-delta.md`](./v3-delta.md) 与总控任务图（MKACG-691）。

### P0 工程基座

目录与分层、依赖矩阵与架构门禁、契约先行、`core` 叶子层、PostgreSQL 存储与版本化迁移。P0 通过是所有后续阶段的前提。

闸门：`alembic upgrade head` 与 `alembic downgrade base` 都退出 0；`pytest tests/architecture -q` 全绿；`backend/app` 下不再有针对已删除的旧存储实现的残留（连接串、方言、建表入口）；契约无漂移。

### P1 交易前准备

建立完整的行情与分析基础设施：`SPOT` / `SWAP` 两类标的的规则集合与可交易集合、市场时段与数据来源治理、全类别夹具、技术指标、动态相关性与关系矩阵、关系网络、市场共振与市场广度、机会发现（目标驱动与市场驱动）、方向性策略与相对价值策略、组合生成与目标组合、策略审批状态机、历史回测。

闸门：一条端到端链路可复现（锚点 → 机会 → 目标组合 → 回测 → 结论，同输入两次 `result_hash` 相同）；回测不读 `as_of` 之后的数据；审批状态机拒绝全部非法转移；两类标的都能跑通同一条链路（追加自 MKACG-740 的 P1 闸门）；`pnpm build` 通过。

### P2 风控管理

策略级风险、全局组合风险、资金分配、风险敞口、集中度、多空冲突与分级风险处置。风控系统独立于策略引擎与交易执行系统。

闸门：未过风控的信号不产生 `OrderIntent`；紧急停止后新信号全被拒且有 `risk_events`；分级处置三档动作可断言；虚拟持仓重复结算幂等。

### P3 交易执行

OKX 账户连接、模拟交易、真实订单执行、持仓同步、虚拟持仓核算、账户对账、故障恢复与自动止损平仓。真实交易默认关闭，需用户明确授权。

闸门：实盘开关默认关闭且未 `acknowledge_risk` 下单返回 409；paper 撮合跑通一条链路；对账能列出「实际持仓 ≠ 虚拟持仓」的差额；断线重连不产生重复订单。

### P4 AI 辅助

进入前单独规划。约束已确定：AI 只做解释与建议，不下单、不绕过风控、不改策略参数、不启动实盘策略。

## 八、开发执行要求

1. 首先检查本地仓库和现有技术栈。
2. 如果项目已经存在，先理解现有结构，不要直接重建。
3. 如果仓库为空，再选择适合本地个人交易系统的技术方案。
4. 先实现完整的数据流和核心功能，不要提前设计未来可能不需要的功能。
5. 每个模块保持独立，公开接口清晰。
6. 核心计算和交易逻辑必须有测试。
7. 所有外部行情和交易数据必须区分真实、模拟及历史数据。
8. 不允许使用模拟数据冒充真实行情。
9. 每个开发阶段都要有可运行结果和验收标准。
10. 当前阶段完成后再进入下一阶段，不要提前实现所有模块。

## 九、项目最终目标

最终形成一个本地个人交易工作台：

我可以在 Watchlist 中观察资产，通过技术指标了解市场状态；在 Strategy 中配置自己的交易逻辑；在 Backtest 中自动测试不同参数和不同资产；在经过验证后，将策略切换成手动交易、模拟交易或自动交易。

系统负责行情、计算、回测、执行和记录。

我负责研究策略、判断风险和决定交易方式。

所有功能围绕这个目标建设，不要将项目扩展成复杂的通用金融 SaaS 平台。
