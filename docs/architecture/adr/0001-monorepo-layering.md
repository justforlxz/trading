# ADR-0001：单仓 Monorepo + 进程内分层，而非微服务

- 状态：已接受
- 日期：2026-11-06
- 相关：`docs/architecture/overview.md`

## 上下文

P1 的负载形态是「227 个标的全市场扫描 + 相关性计算 + 回测」，全部是 CPU/IO 密集的批处理，数据规模在单机 PostgreSQL 可承载范围内（约 3900 万行）。团队是个人自托管，运维预算极低。同时存在四个天然边界：行情采集、分析计算、策略、回测。

## 决策

单仓三目录：`backend/`、`frontend/`、`infra/`。后端是**一个 Python 包**，模块边界用目录 + import 规则守护，不拆服务：

- `adapters`（外部 IO）→ `ports`（协议）← `core`（纯函数）
- `services` 组合三者，`api` / `jobs` 只做协议编排
- 容器维度（`api` / `worker` / `scheduler`）承担伸缩，而不是服务维度

## 后果

正面：

- 跨域事务与查询是本地事务，不需要分布式一致性；策略版本与回测结果的外键约束可以直接生效。
- 一次 `pytest -q` 覆盖全链路；纯函数边界让"可计算即可断言"成立。
- 单机 `docker compose up` 即可部署，与项目"个人自托管"的定位一致。

负面 / 代价：

- 不能独立扩容单个模块；但 P1 的瓶颈是外部限流与计算时长，用 worker 副本数扩容已足够。
- 边界靠纪律维持：需要 `import-linter` 或 CI 的 grep 规则检查禁止依赖（见 overview §4），否则会退化为"大泥球"。
- 全量测试时间随代码增长，需要按目录分组跑。

## 为什么不是其它方案

| 备选 | 拒绝理由 |
| --- | --- |
| 微服务（行情/分析/回测各一服务） | 扫描一次要跨 3 个服务传 227×多周期的中间结果，序列化与重试成本远超收益；引入 4 个部署单元与分布式追踪，个人自托管无法维护 |
| 多仓（backend/frontend/infra 分仓） | 契约变更需要跨仓联动 PR，版本对齐成本高；P1 尚未有外部消费者 |
| 单体但单进程（API 内跑批） | 长任务阻塞请求、重启打断采集；已用 `worker`/`scheduler` 拆出进程，属于同一包的不同入口，仍不是微服务 |

## 复核触发条件

出现以下任一情况时重新评估：单个模块需要独立发布的 API 契约；某模块需要异构技术栈（如 Rust 回测内核）；单次扫描无法在 5 分钟内完成且无法用 worker 水平扩展解决。
