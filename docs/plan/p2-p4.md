# P2–P4 与集成验收拆解（S9 / S10 / S11 / S12）

> 本文档只做**节点拆解**，不实现任何 P2/P3/P4 代码。
> 节点命名沿用 `docs/plan/p1.md` 的 `P<阶段>-<序号>` 约定；每个节点都必须能独立验证（有自己的交付物与可执行 AC），不按「前端一批 / 后端一批」切。
> 阶段门禁沿用主控 issue 的规则：上一阶段全部节点 `done` 后才释放下一阶段；同阶段内节点可并行。

## 0. 拆解原则

1. **阶段边界即 AC**：S9 的 AC 必须包含「无下单/执行代码」，S10 的 AC 必须包含「真实交易默认关闭」，S11 的 AC 必须包含「AI 不能下单、不能绕过风控」。
2. **一个节点一个 PR**：节点 = 可独立合并、可独立验收的最小交付单元。
3. **AC 必须可执行**：每条给命令 + 判定标准，不写「功能正常」这类不可验证描述。
4. **纯函数优先**：风控计算、成本模型、订单状态机等决策逻辑放在 `*/core/` 纯函数里，用已知答案单测覆盖。
5. **不提前实现**：S9 不得引入 `execution/` 目录；S10 不得引入 `ai/`；S11 不得直接读写交易域。

## 5. 依赖图

```
S8 (P1 验收) ──▶ S9 (P2 风控)
                   │
                   ▼
              S10 (P3 执行) ──▶ S11 (P4 AI)
```

## 6. 与 P1 的衔接

- P1 输出的 `docs/reports/p1-smoke-artifacts.json` 是 S9 风控的输入样例（策略腿、权重、回测指标）。
- P1 已知限制中「1h/4h 回补参数上限」与「`partial` 重复入队」属于 S7 遗留缺陷，应在 S9 开始前或并行修复，否则 S10 的实盘链路会受同一问题影响。
- P2 的虚拟持仓模型必须与 P3 的策略级持仓模型共用同一套标识（`strategy_id` + `instrument_id`），避免两套口径。
