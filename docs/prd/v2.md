# trading — 个人量化交易工作台

## 项目定位

开发一个名为 **trading** 的本地个人量化交易研究与执行系统。

这是一个只服务于单个用户的个人工具，不是 SaaS，不需要多用户、多租户、权限体系、团队协作或复杂的云端基础设施。

用户主要通过 OKX 交易代币化美股和加密货币，希望围绕技术指标研究交易策略，调整策略参数，利用历史行情进行自动化回测，并根据策略运行结果选择手动交易或自动交易。

系统的核心工作流程：

市场观察 → 策略配置 → 参数回测 → 结果评估 → 模拟验证 → 手动或自动执行 → 交易复盘。

## 一、核心设计原则

### 1. 以策略为核心

Watchlist 是日常使用入口，Strategy 和 Backtest 是产品核心。

用户主要工作是：
- 观察自己关注的资产。
- 查看 K 线和技术指标。
- 设计交易策略。
- 调整策略参数。
- 对单个或多个资产进行批量回测。
- 根据回测结果选择适合的策略。
- 将策略用于手动交易或自动交易。

不要将产品设计成以财经新闻、股票资讯或 AI 问答为中心的应用。

### 2. 数据驱动，AI 辅助

行情、技术指标、策略信号、回测和订单执行必须由确定性的程序完成。

AI 主要负责：
- 解释市场和技术指标。
- 分析策略表现。
- 辅助理解回测结果。
- 根据用户需求提出策略和参数候选方案。
- 总结交易复盘。

AI 不直接计算行情指标，不绕过策略引擎产生交易订单，也不拥有交易所 API 凭证。

### 3. 模块化但不过度设计

采用模块化单体架构。

每个业务模块有明确职责和接口。

新增技术指标、策略、数据源或交易功能时，尽量通过增加模块实现，不影响已有模块。

不引入微服务、分布式消息系统、复杂插件市场或多 Agent 协作架构。

### 4. 本地优先

- 本地独立运行。
- 使用本地持久化存储。
- 优先使用 SQLite。
- 历史行情较大时允许使用 Parquet 等本地列式文件存储。
- API Key 通过本地配置注入。
- 不要求云端服务或 Kubernetes。

## 二、交易标的

第一版支持 OKX 现货市场与永续合约市场。同一产品的两种形态（例如现货 `XAAPL-USDT` 与永续 `AAPL-USDT-SWAP`）共用行情、指标与策略计算，并能在页面上直接切换。

### 资产类别

**Tokenized Equity**

OKX 上的代币化美股和 ETF，例如：
- XAAPL
- XNVDA
- XTSLA
- XSPY
- XQQQ

**Crypto Spot**

加密货币现货，例如：
- BTC-USDT
- ETH-USDT
- SOL-USDT

**Tokenized Equity Perpetual**

代币化美股的 USDT 本位永续合约，与同产品现货成对，例如：
- AAPL-USDT-SWAP
- NVDA-USDT-SWAP
- TSLA-USDT-SWAP
- SPY-USDT-SWAP
- QQQ-USDT-SWAP

具体可交易资产以当前账户和 OKX API 返回结果为准。

### 交易标的抽象

建立统一的 Instrument 模型。

至少包含：
- symbol / instId
- asset_type
- exchange
- base_currency
- quote_currency
- tick_size
- lot_size
- min_order_size
- listing_time
- trading_status

不同资产可以共用行情、技术指标和策略计算，但交易规则由对应的交易适配层处理。

不能将代币化股票直接视为传统美股。

需要保留交易时间、行情来源、数据可用区间和价格参考机制等信息。

### 现货与永续：同一产品的两种形态

现货（SPOT）与永续（SWAP）都是第一版支持的交易形态。同一个产品的两种形态共用同一套行情、技术指标、策略与回测代码，页面上可一键切换，切换时 K 线周期与指标参数保持不变。两种形态的价格可能因流动性与结算方式而偏离，界面必须同时显示另一形态的最新价与价差，不得暗示两者等价。

永续的价值是做空与杠杆。永续专属的合约参数（`ctVal`、`ctMult`、`ctType`、`maxLever`、`settleCcy`）只在交易适配层与执行/回测的保证金模型中生效，指标、策略与统计模块对形态无感知。

杠杆约束：`max_leverage` 默认 3、硬上限 10，单标的可用杠杆取 `min(max_leverage, instrument.maxLever)`，并按交易所 `position-tiers` 档位 clamp；保证金模式固定逐仓（isolated），持仓模式固定净持仓（net）。这些约束连同强平缓冲与自动止损要求，见「已生效决策」与 `decisions.md`。

资金费是永续持仓的成本：资金费必须计入回测 PnL，且默认开启。

真正的期货合约与更高杠杆档位不在第一版范围，但架构不能阻碍以后增加。

## 三、功能模块

### 1. Exchange

负责交易所连接和数据访问。

第一版实现 OKX Adapter。

负责：
- 获取可交易标的列表。
- 获取最新行情。
- 获取历史 K 线。
- 订阅 WebSocket 行情。
- 获取账户余额。
- 获取当前持仓。
- 查询订单和成交记录。
- 下单、撤单及订单状态同步。

行情接口和交易接口必须分离。

业务模块不能直接调用 OKX API。

交易所适配器负责处理：
- API 签名。
- 限流。
- 断线重连。
- 错误码。
- 请求超时。
- 交易产品精度。
- 订单状态映射。

所有交易请求必须保留本地唯一标识，避免网络重试导致重复下单。

### 2. Market

负责行情管理和历史数据。

支持：
- 最新价格。
- K 线 OHLCV。
- 成交量。
- 行情时间戳。
- 历史行情下载和缓存。
- 数据完整性检查。

统一使用 UTC 时间戳保存数据。

K 线必须能够识别：
- 已完成 K 线。
- 未完成 K 线。
- 缺失数据。
- 重复数据。
- 数据来源。
- 数据更新时间。

对于不同资产，需要允许不同的交易时段和行情连续性。

历史数据不足时，必须明确显示可用起止时间，禁止补造历史数据。

### 3. Watchlist

系统的主要日常入口。

支持：
- 添加和删除标的。
- 按资产类别和自定义分组。
- 搜索标的。
- 查看最新价格及涨跌幅。
- 查看成交量。
- 查看常用技术指标。
- 查看相关标的。
- 查看当前运行策略。
- 查看最近交易信号。
- 设置价格提醒。

Watchlist 支持用户选择资产范围，并将标的集合直接传递给回测模块。

不需要复杂的股票研究管理功能。

### 4. Indicator Engine

建立独立的技术指标计算模块。

第一版实现：
- SMA / MA
- EMA
- RSI
- MACD
- ATR
- Bollinger Bands
- VWAP
- Volume MA

统一指标计算接口。

每个指标需要定义：
- 名称。
- 参数。
- 输入数据。
- 输出字段。
- 计算逻辑。
- 最小数据长度。

新增指标时只需要增加实现并注册，不需要修改策略引擎和界面核心逻辑。

指标计算必须有单元测试，确保历史回测和实时计算结果一致。

支持同一标的多个周期的指标计算。

### 5. Strategy Engine

这是系统最重要的核心模块之一。

建立统一的策略接口。

策略负责读取行情与技术指标，结合用户配置的参数，输出标准化交易信号。

策略不能直接：
- 访问交易所 API。
- 修改账户余额。
- 创建订单。
- 修改持仓。
- 读写其他策略的内部状态。

每个策略必须定义：
- 策略 ID。
- 策略名称。
- 策略版本。
- 参数 Schema。
- 所需指标。
- 所需 K 线周期。
- 信号生成逻辑。
- 信号说明。

统一输出交易信号，例如：

```
{
  "strategy_id": "rsi_mean_reversion",
  "symbol": "BTC-USDT",
  "signal": "BUY",
  "timeframe": "1H",
  "price": 95000,
  "reason": "RSI crossed above oversold threshold",
  "timestamp": "2026-11-10T10:00:00Z"
}
```

信号类型至少支持：
- BUY
- SELL
- HOLD

必要时增加目标仓位或目标仓位比例字段。

第一版实现一些简单策略作为示例：
- MA Cross。
- RSI Mean Reversion。
- MACD Trend。
- Bollinger Bands。

这些示例策略只用于验证架构，不需要一次性实现复杂策略。

策略必须能够独立测试。

### 6. Backtest

这是 P0 核心功能。

建立独立的回测引擎，复用 Strategy Engine 的策略和信号生成逻辑。

不允许回测和实盘分别实现两套策略代码。

#### 回测配置

用户可以选择：

**策略**
- 选择策略。
- 配置参数。

**标的范围**
- 单个标的。
- Watchlist 全部标的。
- 指定分组。
- 用户手动选择的多个标的。
- 当前 OKX 支持的全部可交易标的。

**市场周期**
- 15m。
- 1H。
- 4H。
- 1D。
- 其他实际数据源支持的周期。

**历史区间**
- 开始日期。
- 结束日期。

**资金配置**
- 初始资金。
- 计价货币。
- 每笔交易金额。
- 最大持仓比例。

**交易成本**
- Maker / Taker 手续费。
- 滑点。
- 买卖价差的估算。
- 资金费（仅永续）：按 8 小时结算点、以 `notional × realizedRate` 计入持仓 PnL，正费率多头付出、空头收取；缺失时标记覆盖缺口，不得静默按 0 处理。
- 其他适用费用。

#### 回测结果

每次回测至少输出：

- 初始资金。
- 最终资金。
- 总收益率。
- 年化收益率（适用时）。
- 最大回撤。
- 胜率。
- 盈亏比。
- Profit Factor。
- Sharpe Ratio。
- 交易次数。
- 平均持仓时间。
- 单笔最大盈利。
- 单笔最大亏损。
- 资金费总额与资金费覆盖率（仅永续；覆盖率不足时报告必须显式标注）。
- 数据来源标识（`okx` 或 `us_equity_proxy`）。

同时保存：
- 每笔交易记录。
- 买卖时间。
- 买卖价格。
- 交易数量。
- 手续费。
- 交易原因。
- 收益变化。
- 资金曲线。

#### 批量回测

支持对多个标的执行相同策略。

例如用户选择 RSI 策略，对 Watchlist 中所有资产进行回测，输出资产表现排行榜。

支持：
- 按收益排序。
- 按最大回撤排序。
- 按 Sharpe Ratio 排序。
- 按 Profit Factor 排序。
- 过滤交易次数不足的结果。

区分单标的独立资金回测与多标的共享资金组合回测。

#### 参数组合测试

用户可以为策略参数指定一组候选值。

例如：

RSI Period：7、14、21
Oversold：20、25、30
Overbought：70、75、80

自动组合并执行回测。

保存每组参数的表现，方便横向对比。

不要自动将历史收益最高的参数视为最优参数。

提供训练区间、验证区间和样本外测试区间，帮助发现过拟合。

#### 回测正确性

重点保证：
- 不使用未来数据。
- 不允许未来函数。
- 只使用当时已经完成的 K 线数据。
- 订单成交价格必须符合配置的执行模型。
- 计入交易手续费和滑点。
- 处理同一根 K 线内止盈止损同时触发的歧义。
- 正确管理资金和同时持仓。
- 保留数据缺失和不可交易时段信息。

默认采用 K 线收盘后产生信号、下一根 K 线开盘或可配置执行价格成交的模型。

不同执行方式必须在结果中明确标注。

#### 代理数据源

允许使用真实美股日线行情作为代币化美股的代理回测数据源，用于补足代币化美股上市时间短（约 4 个月）的历史窗口。

代理数据必须遵守：只提供真实存在的周期（真实美股无 24 小时连续行情，不得合成 15m/1H 等周期）；每根 K 线标注来源与 `is_proxy`，与 OKX 行情分表存放；一次回测只使用单一数据源，禁止跨源拼接。代理结果不得与 OKX 实盘标的的回测结果混合排序或聚合，界面以徽标标注「代理数据，与实盘标的不可比」。

### 7. Execution

负责将策略信号转化为订单。

提供三种执行模式：

**Manual**
- 策略生成信号。
- 显示交易计划。
- 用户确认。
- 执行下单。

**Paper Trading**
- 使用真实行情。
- 本地模拟订单。
- 模拟成交、手续费及持仓变化。
- 不产生真实交易。

**Automated Trading**
- 策略信号自动进入执行流程。
- 经过风险检查后下单。
- 同步订单和成交状态。
- 处理订单失败、部分成交和撤单。

策略本身不关心执行模式。

不同执行模式共享策略信号接口。

自动交易默认关闭，需要用户明确启用。

从模拟切换到实盘必须二次确认：请求必须携带显式的风险确认标记，界面弹出二次确认，确认动作写入交易日志留痕。这是提醒而非资格门禁，不设置按天数或成交笔数的硬性门槛。

### 8. Risk Management

负责统一的交易风险约束。

第一版支持：
- 单笔最大交易金额。
- 单个标的最大持仓金额。
- 总持仓资金限制。
- 最大持仓数量。
- 杠杆上限（默认 3、硬上限 10，按档位 clamp）与强平缓冲检查（预估强平价距现价不足阈值时拒绝开仓）。
- 自动模式下开仓必须同时挂交易所侧止损，止损提交失败则整笔不开仓。
- 单日最大亏损。
- 止损和止盈。
- 重复信号防护。
- 订单数量与价格精度检查。
- 账户余额检查。

任何策略都不能绕过风险检查。

提供紧急停止开关。

自动交易发生异常时，默认停止新增订单，并保留当前持仓状态供用户处理。

不要擅自自动清仓。

### 9. Trading Journal

保存完整的策略和交易历史。

包括：
- 策略配置及版本。
- 回测结果。
- 模拟交易记录。
- 实盘交易记录。
- 策略信号。
- 订单及成交。
- 账户资金变化。

支持查看回测结果与实际交易表现的区别。

### 10. AI Assistant

作为后续扩展功能。

允许 AI 读取：
- Watchlist。
- 市场数据。
- 技术指标。
- 策略配置。
- 回测结果。
- 交易日志。

AI 可以：
- 解释当前市场状态。
- 分析技术指标。
- 解释策略表现。
- 提出参数调整候选方案。
- 比较不同策略。
- 总结交易复盘。

AI 可以建议创建策略配置和回测任务，但修改正式策略配置、启用自动交易和执行真实订单必须经过用户明确授权。

AI 不直接接触交易所 Secret Key。

新闻分析不是第一版开发重点，可以在后续增加。

## 四、界面设计

采用现代化、简洁的个人交易工作台设计。

导航建议：

- Overview
- Watchlist
- Strategies
- Backtests
- Trades
- Settings

### Overview

展示：
- 账户资产概况。
- 当前持仓。
- 市场行情。
- 重点关注标的。
- 当前活跃策略。
- 最近交易信号。

### Watchlist

展示标的行情、指标、策略信号及监控状态。

点击标的进入详情，显示 K 线和指标。

### Strategies

展示策略列表。

支持：
- 创建策略实例。
- 配置策略参数。
- 启用或停用。
- 查看策略适用标的。
- 查看策略运行情况。

策略定义与策略实例需要区分。

同一个策略模板可以创建多个独立配置，例如不同周期、不同参数和不同资产范围。

### Backtests

提供回测任务配置、参数扫描、批量标的测试和结果分析。

支持查看历史回测记录及不同参数组合的对比。

### Trades

展示：
- 当前持仓。
- 订单。
- 成交记录。
- 策略信号。
- 交易日志。
- 执行模式。

## 五、数据与架构约束

采用模块化单体。

建议模块边界：

- `exchange`
- `market`
- `instrument`
- `watchlist`
- `indicators`
- `strategy`
- `backtest`
- `execution`
- `risk`
- `journal`
- `shared`

使用清晰的接口和数据模型。

模块不得随意访问其他模块的内部实现。

行情和历史 K 线需要缓存，避免每次回测重复下载。

回测结果必须保存策略版本、参数、数据范围、数据源和执行模型，以确保结果可以复现。

对于大量参数组合和多个标的的回测，使用本地任务队列和有限并发即可，不引入分布式计算系统。

## 六、安全要求

- 默认使用 OKX 模拟盘配置。
- API Key 和 Secret 仅保存在本地。
- 禁止提交凭证到 Git。
- API Key 最小权限原则。
- 禁止开通提币权限。
- 手动交易优先。
- 自动交易必须经过风险检查。
- 自动交易提供全局暂停开关。
- 下单必须进行幂等控制。
- 交易所状态和本地状态不一致时，以重新获取的交易所实际状态进行核对，不能盲目重复下单。

## 七、开发阶段

不要一次性实现全部功能。

### Phase 1：行情和 Watchlist

实现：
- 项目基础框架。
- OKX 行情接入。
- 标的列表。
- 历史 K 线。
- Watchlist。
- K 线展示。

验收：可以在本地查看实际可交易标的的行情和历史数据。

### Phase 2：技术指标

实现：
- Indicator Engine。
- 第一批技术指标。
- 指标参数。
- 图表展示。
- 指标测试。

验收：可以对 Watchlist 中的标的查看多个周期的技术指标。

### Phase 3：策略引擎

实现：
- 统一 Strategy 接口。
- 策略参数配置。
- 第一批基础策略。
- 标准化交易信号。

验收：可以在历史行情上生成可复现的策略信号。

### Phase 4：回测系统

实现：
- 单标的回测。
- 批量标的回测。
- 交易成本模型。
- 参数扫描。
- 回测报告。
- 策略对比。

验收：可以使用同一策略，在不同标的和不同参数下进行批量回测。

### Phase 5：模拟和手动交易

实现：
- 实时策略信号。
- 本地模拟交易。
- OKX 模拟盘接入。
- 人工确认下单。
- 订单和持仓同步。

验收：可以使用已经回测的策略生成信号，并完成模拟或人工确认的交易。

### Phase 6：自动交易

实现：
- 自动执行。
- 风险控制。
- 止损止盈。
- 订单幂等。
- 异常处理。
- 紧急停止。

验收：经过模拟交易验证后，可以对指定策略和标的启用受控自动交易。

## 八、开发执行要求

1. 首先检查本地仓库和现有技术栈。
2. 如果项目已经存在，先理解现有结构，不要直接重建。
3. 如果仓库为空，再选择适合本地个人交易系统的技术方案。
4. 先实现完整的数据流和核心功能，不要提前设计未来可能不需要的功能。
5. 每个模块保持独立，公开接口清晰。
6. 核心计算和交易逻辑必须有测试。
7. 所有外部行情和交易数据必须区分真实、模拟及历史数据。
8. 不允许使用模拟数据冒充真实行情。
9. 每个开发阶段都要有可运行结果和验收标准。
10. 当前阶段完成后再进入下一阶段，不要提前实现所有模块。

## 九、项目最终目标

最终形成一个本地个人交易工作台：

我可以在 Watchlist 中观察资产，通过技术指标了解市场状态；在 Strategy 中配置自己的交易逻辑；在 Backtest 中自动测试不同参数和不同资产；在经过验证后，将策略切换成手动交易、模拟交易或自动交易。

系统负责行情、计算、回测、执行和记录。

我负责研究策略、判断风险和决定交易方式。

所有功能围绕这个目标建设，不要将项目扩展成复杂的通用金融 SaaS 平台。
